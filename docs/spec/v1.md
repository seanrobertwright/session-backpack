## 0. The design in one page

Backpack backs up AI agent sessions into an **encrypted vault** that lives in a folder the user
already syncs. The vault is **append-only and content-addressed**: every captured file becomes an
immutable **blob** named by the BLAKE3 hash of its plaintext, and every backup writes one write-once
**manifest** saying which blobs compose that session at that moment. Nothing is ever rewritten, which
is what makes it safe to put inside OneDrive or Dropbox — the file class that causes sync conflicts
simply does not exist here.

Blobs hold **native bytes only**. Nothing is normalized on the way in, so restore is byte-exact by
construction and a parser improvement in a later release retroactively improves the reading of every
session ever captured.

**Adapters** describe tools; they never touch the vault. The core owns every read, hash, compression,
encryption and write, and vets every path against a deny list no adapter can override. Capture is an
explicit allow-list, because the vault is append-only: a newly-missed file is a next-release bug, a
newly-captured secret is forever.

Everything dangerous is reduced to a **question about bytes**. Are two branches the same story? Compare
blob hashes — the name *is* the hash. May a blob be deleted? Only if a recorded prefix proof
reconstructs it from a blob that still exists. Both are facts, not guesses, and one invariant runs
through the whole design:

> **Deletion never happens on a guess.**

## 1. Product

### 1.1 What Backpack is

A Tauri v2 desktop app for Windows, macOS and Linux that:

1. **Captures** agent sessions and tool state from nine adapters, automatically and continuously.
2. **Stores** them encrypted in a vault inside a folder the user already syncs — **BYO sync**, no
   server, no account, no cloud service of Backpack's own.
3. **Browses** them: a full session reader with a normalized projection across every tool.
4. **Restores** them into a tool's native format on another machine, so the tool's own `--resume`
   just works.
5. **Exports** sanitized plaintext for sharing.

### 1.2 Positioning

*Time Machine for AI agent sessions.* The problem is real and vendor-inflicted: Claude Code deletes
transcripts after 30 days by policy, Gemini CLI after 30 days by default, and no vendor syncs another
vendor's sessions. Multi-tool coverage is the durable moat — even if Anthropic ships sync, it will not
sync Codex sessions ([#8](https://github.com/seanrobertwright/session-backpack/issues/8)).

**One softening is recorded deliberately.** #8 concluded *backup is the product, browsing is supporting
cast*. [#16](https://github.com/seanrobertwright/session-backpack/issues/16) then shipped a full reader
as an equal citizen, with a **global view shape** that governs Home as well as Sessions — so the app no
longer always *opens* on a backup-status band. Navigator leads with the vault, Timeline with a capture
stream. All three shapes still answer *am I safe?* above the fold, but this is a real change of
position and the spec states it rather than letting it arrive unannounced.

The reader declines the fidelity fight with AgentsView (4.8k★, MIT, 40+ tools) on purpose: one
**best-effort normalized projection** that degrades gracefully, not per-format bespoke renderers
([#10](https://github.com/seanrobertwright/session-backpack/issues/10)).

### 1.3 Scope — capture everywhere, restore where the evidence supports it

> **Restore ships in v1 where the format research established a deterministic re-homing path.
> Capture-only where the research flagged an open question or a hostile precondition.**

Capture is byte-copying: cheap, and resistant to format churn. It is not rationed. Restore writes
*into* nine evolving native formats and is rationed by evidence
([#10](https://github.com/seanrobertwright/session-backpack/issues/10)).

| Adapter | v1 | Basis |
|---|---|---|
| Claude Code | **Restore** | Resume survives path changes since v2.1.223 ([#2](https://github.com/seanrobertwright/session-backpack/issues/2)) |
| Codex CLI | **Restore** | Needs only the rollout file at the same relative path ([#3](https://github.com/seanrobertwright/session-backpack/issues/3)) |
| Gemini CLI | **Restore** | Registry + `.project_root` markers make re-homing scriptable ([#4](https://github.com/seanrobertwright/session-backpack/issues/4)) |
| Cline | **Restore** | Portable global JSON ([#6](https://github.com/seanrobertwright/session-backpack/issues/6)) |
| Roo | **Restore** | Portable global JSON ([#6](https://github.com/seanrobertwright/session-backpack/issues/6)) |
| Claude Code VS Code ext | **Restore** | Stores nothing of its own; CLI-owned ([#6](https://github.com/seanrobertwright/session-backpack/issues/6)) |
| pi | **Restore** | cwd-encoded remap understood ([#7](https://github.com/seanrobertwright/session-backpack/issues/7)) |
| oh-my-pi | **Restore** | Same format lineage as pi ([#7](https://github.com/seanrobertwright/session-backpack/issues/7)) |
| Antigravity | **Capture-only** | Open question: do indexes rebuild from disk? ([#5](https://github.com/seanrobertwright/session-backpack/issues/5)) |
| Copilot Chat | **Capture-only** | Always orphans (`md5(path+ctime)`); restore needs a `state.vscdb` index merge with VS Code closed ([#6](https://github.com/seanrobertwright/session-backpack/issues/6)) |

**Capture-only is a statement about missing evidence, not a permanent tier.** An adapter graduates by
implementing `Restorer` — one method and one line, because `restorable` is computed rather than
declared (§5.9). Graduating is deliberately out of scope for v1 as a *release process* question, not
as a technical one.

### 1.4 Kill criteria

Backpack stops being worth building if **both** Anthropic and OpenAI ship account-keyed cross-device
session sync, **or** if AgentsView adds encrypted backup with restore. Recorded so the go decision has
a defined reopening condition rather than being a one-way door
([#8](https://github.com/seanrobertwright/session-backpack/issues/8),
[#10](https://github.com/seanrobertwright/session-backpack/issues/10)).

## 2. Architecture

### 2.1 Process shape

One Tauri v2 application: a **Rust core** and a **Svelte 5 + TypeScript + Tailwind v4** UI
([#9](https://github.com/seanrobertwright/session-backpack/issues/9)).

- Runs as a **tray application** with `tauri-plugin-autostart` and a `--minimized` launch flag.
  Closing the window hides it (`prevent_close()`); backups keep running. macOS uses Accessory
  activation policy while hidden.
- **IPC:** async commands for request/response; `Channel<T>` for backup, restore and export progress
  — ordered high-frequency streams, which is what channels are for. Global events only for
  low-frequency broadcasts. **Payloads stay small; session bodies never cross IPC whole.**

### 2.2 Subsystems

| Subsystem | Owns | Spec |
|---|---|---|
| **Watcher** | `notify` 8.2 + `notify-debouncer-full` 0.7 over declared adapter roots; per-session settle timers | §4.1, §5.7 |
| **Capture pipeline** | Plan resolution, deny-list vetting, stability check, hash, zstd, age, blob + manifest write, prefix proof | §4 |
| **Vault** | Layout, manifest schema, versioning, integrity, conflicted-copy reconciliation | §3 |
| **Crypto** | age 0.12 identities, passphrase wrapping, keychain caching, recipients | §9 |
| **Index** | `rusqlite` 0.40 `bundled` + FTS5 — a **rebuildable per-machine materialized view** of the manifests, plus the projection cache | §2.3 |
| **Adapters** | Detection, enumeration, capture plans, projection, restore | §5, §6 |
| **Compactor** | Weekly idle sweep, proof-chain verification, blob deletion | §8 |
| **UI** | Three view shapes over two nouns, reader, restore and export flows | §10 |

The index is **derived and rebuildable from the vault's manifests**, and lives outside the synced
folder. It is never a source of truth. It exists because enumerating thousands of small manifest files
on every scroll would be slow, and because the projection cache needs somewhere to live.

### 2.3 The local / synced boundary

> **State goes in the vault if and only if another machine needs to know it.**
> ([#13](https://github.com/seanrobertwright/session-backpack/issues/13) §9, ADR 0009)

| State | Where | Why |
|---|---|---|
| Machine id | **Local** | Minting it is this install's business |
| Machine label / os / status | **Vault** | Peers label branches with it |
| SQLite index + projection cache | **Local** | Rebuildable materialized view |
| Quarantine flags | **Local** | One machine's suspicion is not a fact |
| Compaction candidate set | **Local** | Same reason |
| UI preferences (view shape, skin) | **Local** | No peer needs your theme |
| Capture cadence, which installs to watch | **Local** | Governs this install's behaviour only |

The rule settles every case without a special exception. Where a setting would govern *shared*
content, the vault-scoped slot `config/<ts>.mf.age` exists (write-once, newest wins) — but **v1 puts
nothing in it**, because the only candidate was retention and v1 has none (§8).

**Accepted cost:** a fresh install starts from default UI preferences. There is no "adopt my desktop's
setup", because buying that one-time convenience would mean parking presentation state in the shared
append-only vault permanently.

## 3. The vault

Settled by [#11](https://github.com/seanrobertwright/session-backpack/issues/11). ADRs 0001–0004.

### 3.1 Storage model

A **log-structured, content-addressed, append-only archive**. Every capture writes immutable blobs
keyed by the hash of the plaintext, plus a small manifest listing which blobs compose the session at
that moment. Full history, dedup for free, and structural immunity to sync conflicts.

The hash is taken over the **plaintext, before encryption**. age is non-deterministic — a fresh
ephemeral key per file — so hashing ciphertext would defeat dedup entirely. One consequence worth
naming: two machines can write the same blob name with *different ciphertext*. That is harmless. Both
decrypt to identical bytes, so a conflicted copy can be verified and deleted unread.

**Why not a latest-state mirror.** It has no history, so a tool truncating a session syncs the
corruption and the good version is gone; and it makes the vault's only files mutable ones, turning
sync conflicts into a routine event rather than an impossibility.

### 3.2 Layout

age encrypts contents but **never filenames**, so every path component is visible to anyone who can
see the synced folder — the sync provider included. The layout is designed against that.

```
vault/
  vault.json                                       <- plaintext root manifest
  identity.age                                     <- passphrase-wrapped primary identity
  blobs/<hh>/<blake3-hex>.age                      <- immutable, write-once
  sessions/<tool>/<opaque-id>/<machine>/<ts>.mf.age
  state/<tool>/<machine>/<ts>.mf.age               <- settings, MCP configs, memory
  machines/<machine-id>/<ts>.mf.age                <- label, os, status
  config/<ts>.mf.age                               <- vault-scoped settings (unused in v1)

opaque-id = blake3(id_salt || tool || native_id), 128-bit hex
<hh>      = first two hex chars of the blob hash (directory fanout)
<ts>      = 20260814T091233Z-<4 hex>   (suffix avoids same-second collision)
```

**Leaks:** which tools you use, roughly how many sessions, how many machines, when you worked.
**Hides:** project paths, client names, folder layouts, native session ids, machine names.

`<tool>` is readable on purpose — a human with the bare `age` CLI can navigate to a session and
decrypt one manifest. Fully-opaque paths would degrade recovery to decrypting thousands of hashes one
by one, against the recoverability goal §9 sets.

`state/` is a **first-class sibling** of `sessions/`, not an afterthought: the product's scope is full
agent state, and settings, MCP configs and memory belong to a *tool*, not to any one session. It uses
the identical manifest shape with `kind: "toolstate"`.

**One manifest per (session, capture), stored in the session's own directory.** The decisive argument
is blast radius. In a content-addressed store blobs are cheap and manifests are precious — a blob name
is a hash and carries no meaning alone, so the manifest is the only thing that says what a blob *is*.
A damaged per-session manifest costs one session's newest version, and the previous manifest in the
same directory remains a valid, staler description. A damaged per-run journal entry would orphan every
session in that run. The directory tree is itself redundant metadata that survives when the manifests
inside it do not.

A per-run journal was evaluated as an enumeration accelerator and **deliberately deferred**: it is
equally robust only while a "hint, never truth" rule holds, and that is an organizational risk rather
than a technical one. The per-machine SQLite index already does that job (§2.2).

### 3.3 Manifest schema

```jsonc
// sessions/<tool>/<opaque-id>/<machine>/<ts>.mf.age   — age-encrypted, zstd
{
  "v": 1,
  "kind": "session",                        // or "toolstate"
  "tool": "claude-code",
  "tool_version": "2.1.232",                // observed, best-effort
  "adapter_version": 3,

  "session_ref": {                          // absent for kind:"toolstate"
    "native_id": "…",                       // high-entropy, never path-derived
    "native_path": "~/.claude/projects/<encoded-cwd>/<uuid>.jsonl",
    "project": { "path": "C:\\Projects\\acme", "label": "acme" }
  },

  "machine": { "id": "…", "label": "sean-desktop", "os": "windows" },
  "captured_at": "2026-08-14T09:12:33Z",

  "files": [
    { "path": "transcript.jsonl", "role": "transcript",
      "size": 2411920, "blob": "a3f9c2…", "codec": "zstd",
      "supersedes": { "blob": "1b77de…", "len": 2280104 } },
    { "path": "subagents/x.jsonl", "role": "subtranscript",
      "size": 40122, "blob": "7e0b41…", "codec": "zstd" }
  ],

  "meta": {                                 // listing data — browse without decrypting blobs
    "title": "…", "turns": 412,
    "raw_turns": 3, "opaque_turns": 88, "projected_with": 4,
    "first_ts": "…", "last_ts": "…", "total_bytes": 2500000
  },

  "restored_from": {                        // present only on restored sessions
    "opaque_id": "…", "machine": "…", "captured_at": "…"
  },

  "capabilities": { "restorable": true }
}
```

- **`files[].path`** is relative to the tool's own capture root. This is what makes multi-file sessions
  work — Claude Code's `subagents/`, `tasks/` and `file-history/`, Antigravity's `brain/` dirs.
- **`files[].role`** is the hook that lets restore re-home a session and lets the reader know what to
  project. Vocabulary in §5.3.
- **`files[].supersedes`** is the prefix proof; see §8.
- **`session_ref.project`** is *manifest content, never a path component*. Grouping by project costs
  nothing — the reader already decrypts manifests to list anything at all — and keeping it out of the
  filename is what stops a hash of an absolute path reaching the visible surface (§5.5).
- **`meta`** is folded from the projection at capture time (§5.4) and is what the browser lists from.

`vault.json` is **plaintext** and holds: `vault_id`, `format_version`, `min_reader_version`,
`created_at`, `id_salt`, and the primary + recovery age recipients. The wrapped private identity lives
in `identity.age` instead, so the one mutable file in the vault stays tiny and cold.

### 3.4 Format versioning and mixed-version safety

`vault.json` carries `format_version` (bumped for additive change) and `min_reader_version` (bumped
only for a breaking change). Every manifest carries its own `v`.

| Situation | Behaviour |
|---|---|
| Old reader, additive change | Works. Unknown fields ignored. |
| Old reader meets a newer manifest | **That session only** shows *captured by a newer Backpack*. The rest of the vault is fully usable. |
| Build older than `min_reader_version` | Refuse the vault, prompt to update. |
| Any build **writing** | Always safe — append-only, never mutates. |
| **Compactor meets any unparseable manifest** | **Refuse to run.** Tell the user to update. |

This is a hard requirement, not a nicety. §11 ships **prompt-before-install** updates, so a user who
defers on their laptop and accepts on their desktop has two Backpack versions against one shared
vault. Given BYO sync, that is the **main case, not an edge case**
([#15](https://github.com/seanrobertwright/session-backpack/issues/15)).

The last row is the point. Writing is safe by construction, so the only operation that can destroy a
shared vault across a version gap is deletion. Under §8's proof-based compaction the worst case of an
unparseable manifest is a *missed proof* — a failure to delete, which is safe — so this rule is now
defence-in-depth rather than load-bearing. **It is kept anyway**, because compaction is never urgent
and belt-over-braces on the only destructive operation in the system costs nothing.

### 3.5 Integrity and the hydration rule

**Writes** are always temp-file → `fsync` → atomic rename into place. **Blobs are written before the
manifest that references them**, always — §8's safety argument depends on that ordering.

**Reads** decrypt, hash the plaintext, and require it to equal the filename. Integrity is free, because
content addressing already *is* a checksum scheme.

> **No operation ever walks the whole vault reading blobs.**

A hard rule, not a preference. OneDrive Files On-Demand, Dropbox Smart Sync and Google Drive streaming
keep files as cloud-only placeholders, so a full verification pass would hydrate the entire vault:
gigabytes of downloads, a filled disk, and a bill on a metered connection. **Manifests are small and
may be walked freely; blobs may not.** Directory *listings* of `blobs/` are legal and hydrate nothing.

Two targeted carve-outs exist, both reading a named handful of files rather than sweeping: the
conflicted-copy reconciler (§7.5) and compaction's verify-before-delete (§8.4).

A scheduled scrub is therefore rejected. An **opt-in manual integrity check**, with the download cost
stated up front, is available as a later addition.

**Verify-on-read has three outcomes**, not two:

| Outcome | Meaning | Behaviour |
|---|---|---|
| Hash matches | Intact | Proceed |
| Blob absent, proof chain reconstructs it | **Absent by design** (§8) | Reconstruct, verify, proceed |
| Hash mismatch, or absent with no proof | Unavailable | Retry later; escalate only if it persists |

**Quarantine is local state in the per-machine index, never a mutation of the vault.** A partially-synced
blob is byte-for-byte indistinguishable from a corrupted one and will complete on its own; moving files
inside the vault would propagate a false alarm to every machine. A vault-side quarantine move requires
explicit user action.

### 3.6 Conflicted-copy reconciliation

Sync providers resolve their own races by leaving extra files: `file-MACHINE.ext`,
`file (Sean's conflicted copy 2026-08-14).ext`, `file.sync-conflict-<date>-<id>.ext`, `file (1).ext`.
Backpack detects these by filename pattern and resolves them.

| File type | Resolution |
|---|---|
| **Blob** | Decrypt both. Identical plaintext — the normal case, since ciphertext differs but content does not — delete the copy silently. Differing plaintext under one hash-name should be impossible: quarantine and surface. |
| **Manifest** | Write-once and already sharded by machine and timestamp, so a true conflict implies a clock collision. Both are valid facts: keep both, re-slotting the copy under a fresh timestamp. |
| **Machine record** | As manifests, plus: because they fold newest-wins, two copies disagreeing on `status` is not cosmetic. **Surface it to the user** rather than resolving by timestamp. |
| **`vault.json`** | The only mutable file in the vault, and so the only routine conflict candidate. Take the higher `format_version`, union the recipients, surface any `vault_id` disagreement. |

**Who reconciles: any machine, opportunistically, during work it was doing anyway.** Conflicted copies
are found by directory listing — cheap, and legal under the hydration rule. Resolving a blob conflict
then hydrates exactly the two files involved.

A designated reconciler machine was rejected: the designation is contended mutable state, and if that
machine is lost or retired, conflicts accumulate forever with nothing to clear them — a silent failure
that worsens with time. **Work that is safe from anywhere should not be assigned to somewhere, because
assignment can only add a way for it to stop happening.**

One rule attaches: **a machine that cannot parse a manifest must not delete its conflicted copy.** Same
invariant as §3.4's last row, in its second location.

## 4. Capture

Settled by [#21](https://github.com/seanrobertwright/session-backpack/issues/21), measured against
1,065 real Claude Code transcripts (739 MB, 31 days) on the dev machine.

### 4.1 Triggers

**Capture fires on idle-settle alone.**

- **Settle: 90 s.** A session is captured 90 seconds after writes to it stop.
- **Floor: 10 min.** Minimum interval between two captures of the same session, so a chatty session
  cannot spin.
- **No ceiling.** A session that never idles is never captured, and that hole is accepted.

The hole is small and the reasoning is measured, not assumed: across 50 large sessions every one had
between 2 and 25 idle gaps of 90 s+, and the **longest gap-free run was 36 minutes**. The decisive
argument is that **the transcript is already durably on local disk** — a missed capture only loses data
if the *machine* dies inside that window. The threat model is vendor deletion at 30 days and machine
loss, not process crash: a crashed agent leaves its JSONL sitting there for the next enumerate.

The 30-day upstream deletion in Claude Code and Gemini CLI is a **deadline, not a frequency**. It argues
for capturing within days, not within seconds.

Two triggers are not idle-settle:

- **Startup catch-up.** The watcher only sees writes while Backpack runs, and the common laptop case is
  that it did not. On startup the core enumerates every adapter root and captures anything whose
  fingerprint moved since its last capture — **immediately, no settle and no floor.** The settle timer
  exists to avoid capturing mid-write, and the stability check covers that directly.
- **Manual backup.** Shares the entire capture path and bypasses both timers, but **not the fingerprint
  diff**: "Back up now" on unchanged sessions mints no blob and, more importantly, **no manifest**.
  Manifests are write-once and permanent, so a manual path that minted an empty capture per session
  would let a user grow the vault permanently by clicking a button. Unchanged sessions report *already
  up to date*. And because the user pressed a button, **its failures are loud**: manual retries the
  stability check briefly, then surfaces still-busy sessions as explicitly skipped.

Both paths reset the session's floor naturally — the floor is just *time since this session's last
capture*.

**The policy is one global constant. It is not per-adapter and not user-visible** — no slider, no
advanced pane. All six format-research tickets found the same rhythm (append-on-turn), so per-adapter
tuning is unjustified by the evidence; `settle_ms` on `AdapterDescriptor` remains a purely additive
escape hatch if that ever changes. Hiding it was the harder half, since cadence spends the user's paid
sync quota — taken anyway because the knob does not actually give them control of that. Vault size is
dominated by session count and size once cadence is sane; a slider lets a user make it much worse and
only marginally better.

### 4.2 Atomicity — the requirement is a record-boundary prefix

**Capture needs no atomicity mechanism.** Under §3's append-only history, a blob containing the first
400 of 500 turns is byte-identical to what a capture ten minutes earlier would have contained. **It is
not damage; it is a version.** Nothing needs to detect it, because nothing is wrong with it.

The actual requirement:

> **Every blob must be a byte-exact prefix at a record boundary — a state the file genuinely passed
> through.**

The only invalid outcome is a **torn record**: a byte-level partial write producing a state the file
never actually had. And that failure is *loud rather than silent*, which is the useful direction:
measured record lengths run p50 740 B, p90 3.5 KB, **max 691 KB** (one inline base64 image). No OS
writes 691 KB atomically, so the realistic mid-write failure is a torn final line that **fails to
parse**, not a clean line-boundary prefix.

**The guard is one group-wide stability check.**

- **Stat → read → stat, bracketing every file `plan_capture` returned for one session** — not each file
  independently.
- If size or mtime moved anywhere in the group, **discard the entire attempt and re-arm the settle
  timer.**
- **Not a retry loop.** The writer is evidently active again; let the next 90 s of idle come around. It
  cannot spin, idle-settle guarantees another chance, and a discarded attempt is not a capture, so the
  floor does not block it.
- **A read that fails — including a Windows sharing violation — is treated identically**: discard and
  re-arm. Tested rather than assumed: copying a live Claude Code transcript mid-write succeeded
  byte-identical, so Claude Code takes no exclusive read lock.
- **Never truncate to the last valid record.** That would be the core editing file *contents*, which is
  the line capture and restore both refuse to cross (ADR 0006), and a trimmed blob is no longer native
  bytes.
- **A torn tail that lands anyway needs no new machinery**: it projects as `Body::Raw` — failure, always
  visible (§5.4) — the manifest's counts drive the advisory `partial` badge, and the next capture
  supersedes it.

Widening the check from per-file to per-group is what lets one rule cover append-only transcripts,
`.db` + `-wal` pairs and artifact directories identically.

### 4.3 SQLite — no special mechanism at all

Header inspection settled this. Antigravity is WAL mode with one database per conversation, and **its
WAL is empty in practice**: of 33 conversations only 3 carry a `-wal` sidecar and all 3 are zero bytes,
because SQLite checkpoints on close and only a *live* conversation holds pending WAL content. Since
captures fire after 90 s idle, we are essentially always copying a fully-checkpointed database. VS Code
and Cursor are **not WAL at all** — rollback-journal mode, each `state.vscdb` beside a same-size
`.backup`.

- **Capture `.db` and `-wal` together as native bytes; exclude `-shm`.** The shm is a rebuildable
  shared-memory index whose contents are process-local and meaningless on another machine. In v1 this
  rule applies to exactly one thing: Antigravity's per-conversation `conversations/<id>.db`.
- **VS Code's `state.vscdb` is never captured at all.** It is on the core deny list (§5.2), because it
  holds Antigravity's plaintext `apiKey` and every extension's `secret://` rows. Its same-size
  `.backup` sibling is denied with it. *(Recorded because the cadence and vault-format tickets
  disagreed on this point — see the note at the end of this section.)*
- **Never open a database with SQLite during capture.** This is decisive against the textbook
  alternatives. Opening a WAL database **writes to disk even read-only**: it creates or updates `-shm`
  and can trigger WAL recovery that modifies the main db. *A backup tool must not mutate the thing it
  is backing up.* `VACUUM INTO` additionally forfeits byte-exact restore — its output is semantically
  equal but not byte-equal.

**Accepted residual:** for append-only files a slipped-through tear yields a partially-readable
transcript; for SQLite it yields an **unopenable database**, a worse failure. Accepted because zero of
33 conversations carry WAL content, append-only history means the next capture supersedes it, and
`Body::Raw` makes an unprojectable database loud rather than silent.

> **Conflict resolved here.** [#21](https://github.com/seanrobertwright/session-backpack/issues/21)
> proposed capturing `state.vscdb.backup` alongside `state.vscdb` as *"a free consistent fallback"*,
> while [#12](https://github.com/seanrobertwright/session-backpack/issues/12) had already placed
> `**/*.vscdb` and `**/*.vscdb.backup` on the core deny list and stated that VS Code's `state.vscdb`
> is *"simply never in a plan"*. **#12 wins**, on its own reasoning and on the deny list's whole
> premise: those files carry live credentials, and under an append-only vault a captured secret is
> unfixable. #21 was reasoning about SQLite capture *mechanics* and did not argue for overriding the
> deny list. The `.backup` observation is retained above as **context for a future Copilot/Roo restore
> path** — where Backpack would *write* the index, not capture it — and not as a capture rule.



### 4.4 The pipeline

For each session at settle:

1. `enumerate()` + fingerprint diff (§5.7). No change → stop.
2. `plan_capture()` → an allow-list of paths (§5.2).
3. Core resolves the paths and **vets every one against the deny list**. A hit fails the capture
   loudly.
4. Group-wide stat (§4.2).
5. Read each file. Hash the plaintext (BLAKE3). While the bytes are in hand, compute the **prefix
   proof** against the previous capture's blob and length (§8.2).
6. Group-wide stat again. Any movement or read failure → **discard everything and re-arm**.
7. `project()` the transcript roles once, to fold `meta` (§5.4).
8. zstd, then age to both recipients. Write blobs first (temp → fsync → rename).
9. Write the manifest.
10. Update the local index.

### 4.5 Growth budget

Simulated over all 1,051 sessions with usable timestamps, under the shipped policy:

| Metric | Value |
|---|---|
| Captures per session | **p50 = 1**, p75 = 2, p90 = 5, p99 = 12, max 20, **mean 2.1** |
| Baseline (1 capture/session) | 0.69 GiB / 30 days |
| Under policy | 2.24 GiB / 30 days |
| **Amplification** | **3.26×** |
| Compression (gzip-9 sample; zstd-19 typically 10–15% better) | **4.32×** |
| **Real vault cost** | **~0.5 GiB / 30 days ≈ 6.3 GiB/year, per tool per machine** |

The median session gets exactly one capture — the policy working as designed. The growth is
concentrated entirely in the chatty p90 tail, which is also exactly where §8's compactor reclaims.

This matters because the vault lives in *the user's* synced folder, and the free tiers are OneDrive
5 GB, Dropbox 2 GB, Google Drive 15 GB. A two-tool user on two machines crosses OneDrive free inside a
year. Not ignorable — but not urgent either, which is what buys §8's very large safety margins.

**Delta storage is deliberately deferred.** Whole-file addressing of an append-only log is
O(size × captures), and 3.26× is precisely the prize an additive `segments[]` manifest field would win.
It is retrofittable without a format break, §8's compactor claims most of that prize with no new
encoding at all, and segmentation's real cost is that a session's newest version needs its whole
segment chain — a lost early segment orphans everything after it, and reading means N hydrations on
cloud-tiered storage. Whole-file blobs keep every stored version independently complete: **lose one
blob, lose exactly one version.**

## 5. Adapters

Settled by [#12](https://github.com/seanrobertwright/session-backpack/issues/12), amended by
[#18](https://github.com/seanrobertwright/session-backpack/issues/18) and
[#21](https://github.com/seanrobertwright/session-backpack/issues/21). ADRs 0005, 0006.

An adapter is a **near-pure description of one tool, not an agent that acts on the vault.** The core
owns every byte that enters or leaves: it reads, hashes, compresses, encrypts and writes. The adapter
says *what* and *where*, and parses bytes into turns.

**One exception is carved out deliberately — restore — and the reason it is the only one is the shape
of the evidence:** across all six format-research tickets, every tool's capture is *"copy these files"*,
but every tool's restore is different work.

### 5.1 The trait

```rust
pub trait Adapter: Send + Sync {
    fn descriptor(&self) -> &AdapterDescriptor;

    /// 0..n installs of *this* tool on this machine.
    fn detect(&self) -> Vec<Install>;

    fn enumerate(&self, install: &Install) -> Result<Vec<SessionRef>>;
    fn enumerate_state(&self, install: &Install) -> Result<CapturePlan>;

    /// PURE. No I/O. Core resolves, vets, reads, hashes, zstd, age, writes.
    fn plan_capture(&self, s: &SessionRef) -> Result<CapturePlan>;

    /// PURE. Native bytes in, turns out. Called at read time to render,
    /// and at capture time solely to fold out the manifest's `meta`.
    fn project(&self, input: ProjectInput) -> Result<Projection>;

    /// Absent = capture-only. This *is* the capability declaration.
    fn restorer(&self) -> Option<&dyn Restorer> { None }
}

pub trait Restorer: Send + Sync {
    /// Core has already decrypted + verified the blobs into `staged`.
    fn restore(&self, staged: &StagedSession, target: &Target) -> Result<RestoreOutcome>;
}

pub struct SessionRef {
    pub native_id:   String,
    pub fingerprint: Fingerprint,   // transcript mtime + size
    // …
}
```

`plan_capture` and `project` are pure functions — trivially unit-testable against a fixture directory,
and **structurally incapable of writing plaintext anywhere**. `detect`, `enumerate` and `restore` do
I/O because they must: Gemini enumeration reads `projects.json`, Antigravity's reads SQLite.

A symmetric contract was rejected in both directions. *Pure planner both ways* would need the core to
interpret a step language rich enough for a SQLite index merge and a path-hash re-key — that language
becomes the hard part and grows with every tool. *Adapter executes both* re-implements age, zstd and
secret handling per adapter, and would let an adapter write plaintext into a vault sitting in the
user's OneDrive.

### 5.2 Capture is an allow-list, backstopped by the core

The adapter names exactly what it wants. **Nothing is captured implicitly.**

```rust
CapturePlan {
    root: "~/.claude/projects/<encoded-cwd>",
    files: vec![
        Include::file("<uuid>.jsonl",      FileRole::Transcript),
        Include::glob("subagents/*.jsonl", FileRole::Subtranscript)
            .with_companion("subagents/{stem}.meta.json"),
        Include::glob("tasks/**",          FileRole::Sidecar),
    ],
}
```

Before any read, the core vets every resolved path against a **non-overridable deny list**. A plan that
hits it **fails hard rather than silently dropping the file** — a silent drop hides an adapter bug, a
hard failure surfaces it.

```
**/.credentials.json            Claude Code OAuth (#2)
**/auth.json                    Codex OAuth refresh (#3), pi (#7)
**/agent.db                     oh-my-pi — plaintext tokens in SQLite (#7)
**/oauth_creds.json             Gemini (#4)
**/installation_id, **/trustedFolders.json
**/*.vscdb, **/*.vscdb.backup   Antigravity plaintext apiKey (#5), VS Code secret:// rows (#6)
**/.env, **/id_*, **/*.pem, **/*.key
```

The deny list is **defence in depth, not the primary mechanism** — a correct adapter never trips it.
Its job is to hold when an adapter is wrong, when a tool starts writing a new credential file, and when
the adapter came from someone else.

**Why not a deny-list capture root.** A root-and-exclude model auto-adopts new files a tool starts
writing, so adapters rot more slowly. But the failure is inverted and permanent: the vault is
append-only, so the day a tool drops a token cache into a captured directory, it is in the vault
forever. **Missing a newly useful file is a correctness bug you fix in the next release; capturing a
new secret is not fixable at all.**

Two things follow for free. Codex's rebuildable SQLite index and VS Code's `state.vscdb` are simply
never in a plan, so there is nothing to tag as skippable. And Copilot's index-merge problem leaves v1
alongside the restore it was blocking.

### 5.3 `FileRole`

```rust
#[derive(Serialize, Deserialize)]
#[serde(rename_all = "kebab-case")]
pub enum FileRole {
    // kind: "session"
    Transcript,     // the conversation stream; projected. May repeat, ordered.
    Subtranscript,  // a subagent's transcript: projected, never concatenated
    Sidecar,        // restored verbatim, never projected
                    //   Claude Code tasks/ file-history/, Antigravity brain/,
                    //   Gemini checkpoint-*.json + shell_history

    // kind: "toolstate"
    Settings,       // settings.json, config.toml
    Mcp,            // .mcp.json, mcp_servers.toml
    Memory,         // CLAUDE.md, GEMINI.md, AGENTS.md, memory/

    #[serde(other)]
    Unknown,        // forward-compat under §3.4: never a parse error
}
```

The session roles are split by **how the reader and restore must treat a file**. The toolstate roles
are split by something else entirely: **that is where selective restore actually gets asked for.**
*"Bring my MCP servers, not my keybindings"* is a
real request, and the files answering it sit at different paths in every tool — so a cross-tool UI
needs the tag rather than a per-tool path table. Sessions have no equivalent, because a session is
restored as a unit.

An `Attachment` role and a `Merge` role were both rejected. `Merge`'s only v1 candidate was Copilot's
`state.vscdb`, now denied and capture-only. `Attachment` became a **body** variant instead (§5.4),
which is where it belonged.

### 5.4 Projection

> **The projection is a faithful superset. `project()` emits a `Turn` for every record in the file, and
> the reader filters.**

This is the load-bearing choice and everything else follows from it. **What an adapter drops is gone
until someone ships a new `adapter_version`; what the reader hides is a checkbox.** Since blobs hold
native bytes only and projections are derived at read time, the whole design already bets on *a later
parser fix retroactively improves all history* — and a curated projection is the one place that bet
would be silently voided.

```rust
fn project(&self, input: ProjectInput) -> Result<Projection>;

pub struct ProjectInput<'a> {
    pub bytes:     &'a [u8],
    pub role:      FileRole,
    pub companion: Option<&'a [u8]>,   // declared in CapturePlan, resolved by core
}

pub struct Projection { pub turns: Vec<Turn>, pub label: Option<String> }

pub struct Turn { pub role: TurnRole, pub ts: Option<Timestamp>, pub body: Body }

pub enum TurnRole { User, Assistant, System, Tool }

pub enum Body {
    Text(String),
    ToolCall  { name: String, summary: String },
    Thinking(String),                                  // collapsed by default
    Attachment { kind: AttachmentKind, media_type: String,
                 name: Option<String>, size: u64, span: Option<Span> },
    Opaque    { kind: String },                        // deliberate: known, judged uninteresting
    Raw       { bytes: Vec<u8> },                      // FAILURE: content expected, parse failed
}

pub struct Span { pub offset: u64, pub len: u64 }
```

**`Opaque` and `Raw` are different things, and the type says so.** A single `Raw` would mean two
opposite things — *"a hook fired and I didn't bother decoding it"* and *"this is conversation content
and my parser failed"*. The first should be hidden; the second must never be. Splitting them makes it
**structurally impossible for a parser bug to disguise itself as noise**. `Opaque` carries the native
type string (`"hook_success"`, `"bridge-session"`) so revealing it is meaningful.

A single `Raw` plus a `visibility` flag was rejected: nothing stops an adapter stamping *hidden* on a
genuine failure, which is exactly the lie the split prevents. Inferring from `TurnRole` was rejected on
the live case — Antigravity's undecodable protobuf has no reliable role *until it is decoded*, so the
failure would land in the hidden bucket. Worst possible outcome, for free.

**`Attachment` carries a descriptor plus an optional `Span` into the native file, never a payload.**
Images are **inline base64** — one sampled 19 MB session is 38% base64 — so carrying payloads would
bloat the per-machine projection cache for content the reader can slice on demand from a blob it has
already decrypted. `span: None` where offsets are meaningless (Antigravity's SQLite/protobuf),
degrading to a chip.

**`ProjectInput::companion` is one narrow declared channel, not a general cross-file one.** It exists
because Claude Code's subagent thread label lives *only* in `agent-<id>.meta.json`, never in the
`.jsonl`, whose first record is raw prompt text. The adapter names the companion in its `CapturePlan`;
the core resolves it and vets it against the deny list like any other path. `project()` stays pure and
does no I/O.

**Where it runs: read time**, cached in the per-machine SQLite index keyed by
`(blob_hash, adapter_version)`. The multi-machine case decides this before cost is even considered:
machine A captures, machine B reads, and anything A computed at capture time lives in A's local index
where B cannot see it. Read-time derivation is therefore mandatory regardless.

**One entry point, not two.** The core calls the same `project()` at capture time purely to fold `meta`:

```rust
let meta = adapter.project(input)?.fold_meta();
```

A separate cheap `scan_meta()` would avoid full parsing on captures nobody opens, at the price of two
parsers per adapter — eighteen across nine adapters — that can disagree about a session's turn count.
The same bytes already take a zstd and an age pass, so parsing is not where capture spends its time,
and **`meta` and the reader are now incapable of disagreeing.**

**Degradation is per-turn.** `project()` always returns a turn sequence; `Err` is reserved for input so
broken that turn boundaries cannot be found at all. This matters because `meta` is folded from the
projection: an all-or-nothing parser would write `title: null, turns: null` into the vault permanently,
at capture time, for a session nobody may open for a year. **Antigravity is the live case** — full
protobuf decoding is genuinely uncertain, but the SQLite layer alone yields row counts and timestamps,
so it can report N turns with real timestamps and `Body::Raw` bodies without decoding a single message.

### 5.5 Session identity

> **Session id is always the tool's own session-level identifier. An adapter must never feed a
> path-derived value into `blake3(id_salt || tool || native_id)`.**

`id_salt` must be **plaintext**, because unattended backup has to compute opaque ids without ever
unlocking the vault (§9.2). Opaque ids are therefore preimage-resistant but **not resistant to a
confirmed guess**: someone with folder access who guesses a `native_id` can test whether that session is
present.

That risk is **avoidable outright rather than merely narrowed**, because both cases that appeared to
threaten it are misdiagnosed at the session level:

- **Copilot Chat** — sessions are `chatSessions/<uuid>.jsonl`. Only the *workspace directory* is
  `md5(folderFsPath + folderCreationTimeMs)`.
- **Gemini CLI** — current JSONL carries `sessionId` in its header line. Only the *project directory* is
  `sha256(<abs path>)`.

In both tools the path-derived hash identifies the **project**, not the session. Cline's
`tasks/<epoch-ms>/` is low-entropy but not path-derived, and leaks only *you used Cline that day* —
which the manifest's `<ts>` filename already discloses. **So the rule costs nothing.**

Project and workspace are therefore **manifest content** (`session_ref.project`, §3.3), which is
encrypted. A `<project-hash>` path component was rejected: it would group on a cold vault without
unlocking, but it puts a hash of an absolute path back on the visible surface, restoring exactly the
weakness the rule eliminates.

### 5.6 Restore

```rust
pub struct Target {
    pub install:      Install,
    pub project_path: PathBuf,   // where it lands on THIS machine
    pub on_collision: Collision, // RESOLVED by the UI before the call
}
```

**Re-homing is intrinsic, not a feature.** Machine B rarely has machine A's paths; a different absolute
path orphans Gemini sessions, and Copilot's workspace hash differs per machine by construction. A
verbatim-paths restore would, in the main case, write files the tool never looks at.

The core decrypts and verifies blobs into `staged` first, so `Restorer` **never touches the vault**, and
`on_collision` arrives already decided — the adapter executes a policy, it does not author or prompt for
one. Adapter-proposed target candidates were rejected: scanning for like-named projects and ranking them
is the UI's job, not the contract's.

**Restore rewrites placement, never contents** (ADR 0006). §7.2 covers session identity across restore.

### 5.7 Watching

`AdapterDescriptor.watch_roots` declares **local agent directories only**. The vault is **never**
watched — watching it would make Backpack's own writes trigger its next capture.

On a debounced OS event the core re-runs `enumerate()` and captures any `SessionRef` whose fingerprint
changed. This adds no trait method: change detection reuses the one function adapters already implement,
so there is no second notion of session identity that can drift from enumeration. A
`session_for_path()` reverse map was rejected for exactly that reason — it gets fuzzy on multi-file
sessions (`file-history/abc.txt`, `brain/<x>/note.md` — which session owns them?).

Two refinements fix what the contract originally left open:

- **The settle timer is keyed on the session, not the watch root.** `~/.claude/projects` holds 1,065
  files across many projects; a per-root timer would let one busy session indefinitely postpone the
  capture of a quiet one that finished an hour ago.
- **`enumerate()` + fingerprint diff runs once at settle**, not on every debounced event batch.
  Re-enumerating a thousand-file tree every few seconds during an active session is pure waste. A path
  event that maps to no known session triggers an enumerate to learn the mapping — that is how new
  sessions are picked up.

This leaves the `notify-debouncer-full` window as what it should be: short library-level coalescing of
OS events, not a policy lever.

**Watch roots overlap, and the core must handle it.** `~/.gemini` is shared by Gemini CLI and all three
Antigravity roots. The core deduplicates OS-level watches and fans one event out to every adapter whose
roots contain it. Per-adapter watchers would double-register on that tree and fire twice for every
event.

### 5.8 Registry

`descriptor().id` **is** the vault namespace and a **permanent format constant** (ADR 0002). The tool
name is a path component and the vault is append-only, so renaming an id after v1 orphans every session
captured under the old one. **This is not a migration that can be performed.**

Two multiplicities are kept apart:

- **Several installs of one tool** — VS Code Stable / Insiders / VSCodium, Antigravity's three roots —
  collapse into one namespace via `detect() -> Vec<Install>`.
- **Distinct tools sharing a format** — oh-my-pi is a hard fork of pi with an identical JSONL session
  tree — are **separate adapters over a shared module**:

```rust
mod pi_format { /* shared enumerate / plan / project */ }

pub struct Pi;       // id "pi",       root ~/.pi/agent
pub struct OhMyPi;   // id "oh-my-pi", root ~/.omp/agent
```

Merging the fork into one id was rejected precisely because it is unfixable: `sessions/pi/` would
permanently hold both tools' sessions with no way to tell them apart, and restore could not infer the
target tool. A few lines of duplication buys a flat registry and an unambiguous id → adapter lookup
everywhere.

Adapters are **compiled in**. "Without touching core" is satisfied by the trait boundary: a new adapter
is one module of pure functions plus one registry line, needing **zero** changes to capture, vault,
encryption, watching or UI. Third-party adapters without a rebuild are out of scope (§12).

### 5.9 Capabilities and versioning

`restorer().is_some()` **is** the capability declaration. The core stamps it onto every manifest as
`capabilities.restorable`. Never hand-maintained, so *cheap to flip* is literal: an adapter graduates
from capture-only by implementing `Restorer` and returning `Some(self)`, and the type system carries it
from there. Because it is stamped **per manifest** rather than read from the adapter at display time, a
session captured while an adapter was capture-only stays honestly labelled after that adapter graduates.

**No other capability flags exist**, because every other partial capability is already expressed by a
return type:

| Partial capability | How it is expressed |
|---|---|
| Cannot restore | `restorer()` returns `None` |
| Has no toolstate | `enumerate_state()` returns an empty plan |
| Cannot decode turn bodies | `Body::Raw` per turn |
| Cannot parse at all | `project()` returns `Err` → raw view |
| Not installed | `detect()` returns `vec![]` |

**`adapter_version`** is a single integer per adapter, bumped on any observable behaviour change —
capture list or projection. It keys the projection cache (a bump silently reparses) and is recorded on
the manifest so a capture can be traced to the adapter build that produced it. Over-invalidation is
harmless: reparsing is cheap and the native bytes are always present.

## 6. The nine adapters

Grounded in [#2](https://github.com/seanrobertwright/session-backpack/issues/2)–[#7](https://github.com/seanrobertwright/session-backpack/issues/7),
each verified against a live install. The linked research reports carry full capture globs, watch paths
and step-by-step restore procedures; this section is the design-relevant summary.

**Two facts apply to every adapter and are not repeated below:** transcripts contain anything the user
ever pasted, so the vault is encrypted regardless of the tool; and no credential file travels, ever —
re-authentication on the target machine is an explicit, expected restore step.

### 6.1 `claude-code` — Claude Code · **restore**

- **Root:** `~/.claude/` (relocatable via `CLAUDE_CONFIG_DIR`), plus `~/.claude.json`.
- **Session:** one append-only JSONL at `~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl`, where
  `<encoded-cwd>` is the absolute path with non-alphanumerics replaced by `-` (lossy; the true path is
  in each record's `cwd`). Native id = UUIDv4 = filename. Records chain `uuid → parentUuid`.
- **Multi-file:** `projects/<enc>/<uuid>/subagents/agent-<id>.jsonl` (**`Subtranscript`**, each with an
  `agent-<id>.meta.json` **companion** carrying `agentType`, `description` and `toolUseId`),
  `~/.claude/tasks/<uuid>/` and `~/.claude/file-history/<uuid>/` (`Sidecar`).
- **Resume:** since v2.1.223, `--resume <id>` searches all projects on the machine, so **a differing
  project path does not break resume** — but the id must resolve to exactly one transcript, so restore
  must never leave duplicate copies under two project folders.
- **Restore:** write to `projects/<munge(project_path)>/`, re-encoding the subagent dir under the
  destination folder name.
- **Deny:** `.credentials.json` (plaintext OAuth access + refresh on Windows/Linux; macOS uses the
  Keychain). Also excluded as machine-local runtime state: `shell-snapshots/`, `session-env/`,
  `sessions/`, `ide/`, `daemon*`, caches.
- **Gotcha:** **30-day transcript auto-cleanup** (`cleanupPeriodDays`) — capture cadence must beat it.
  The transcript format is explicitly version-internal: copy, never rewrite.

### 6.2 `codex` — Codex CLI · **restore**

- **Root:** `CODEX_HOME`, default `~/.codex` on every OS — a plain dotfolder, no AppData or XDG. CLI,
  TUI, VS Code extension and Codex Desktop **all share it, so one adapter covers every Codex surface.**
- **Session:** `sessions/YYYY/MM/DD/rollout-<ISO-ts>-<uuidv7>.jsonl`, append-only. First line
  `session_meta` (session_id, cwd, originator, cli_version, git repo/branch/commit), then
  `turn_context`, `response_item`, `event_msg`. Each resume appends a fresh `session_meta` with the same
  id.
- **Identity:** **UUIDv7** — time-ordered and globally unique, so **multi-machine merges are
  collision-free.**
- **Restore:** the rollout file at the same relative path under the target `CODEX_HOME`. That is the
  whole travel set. `state_5.sqlite` stores absolute paths and is a **rebuildable derived cache** — never
  captured, never restored (~1.5 GB of rebuildable state here versus ~158 MB of sessions).
- **Deny:** `auth.json` (ChatGPT OAuth id/access/**refresh** tokens, or `OPENAI_API_KEY`). `config.toml`
  can embed MCP API keys in args and env — captured as `Settings`, and flagged on restore (§7.4).

### 6.3 `gemini-cli` — Gemini CLI · **restore**

- **Root:** `~/.gemini` on every OS.
- **Session:** `tmp/<project-id>/chats/session-*.json(l)` — legacy single-JSON, current append-only
  JSONL with a header line carrying `sessionId`, `projectHash`, `kind`. **Native id is the header's
  `sessionId`, never the directory hash** (§5.5).
- **The critical fact: a different absolute path orphans sessions.** Legacy dirs are
  `sha256(<exact absolute path string>)`, case- and separator-sensitive. Current v0.55.x uses human slug
  dirs plus a registry `~/.gemini/projects.json` mapping normalized path → slug (resolve; **lowercased
  on Windows only**), with `.project_root` ownership markers inside each dir.
- **Restore:** upsert the `projects.json` entry and **rewrite `.project_root`** to the new normalized
  path. If the marker is not rewritten, ownership verification silently discards the mapping. Slug
  collisions on the target need the CLI's own `name-1` dedupe loop. `--session-file <json>` is a
  registry-surgery-free fallback path.
- **Travels:** `tmp/<id>/{chats, checkpoint-*.json, shell_history, memory, .project_root}` (checkpoints
  and shell history as `Sidecar`), the project's `projects.json` entry, `GEMINI.md` (`Memory`),
  optionally `settings.json` and `commands/`.
- **Deny:** `oauth_creds.json` (plaintext by default; the opt-in encrypted fallback is AES-256-GCM keyed
  on hostname+username, i.e. **cryptographically machine-bound**), `installation_id`,
  `trustedFolders.json`. Skip `history/` shadow git repos, `tool-outputs/`, extensions.
- **Gotcha:** **30-day auto-delete** (`general.sessionRetention`, cascading) — and mind *target-machine*
  retention on restore. `~/.gemini` is **colonized by non-CLI tools** (Antigravity, frameworks): strict
  allow-list globs, never `tmp/**` wholesale.

### 6.4 `antigravity` — Antigravity CLI + IDE · **capture-only**

- **Roots:** `~/.gemini/antigravity/` (IDE), `~/.gemini/antigravity-cli/` (agy CLI),
  `~/.gemini/antigravity-ide/` (newer IDE channel) — three installs, one adapter.
- **Session:** a conversation, UUIDv4. Same UUID names `conversations/<id>.db` (SQLite in **WAL mode**,
  protobuf blobs in a `steps` table) or `<id>.pb` (older single-blob format; a migration was observed
  mid-2026), `brain/<id>/` (task.md, implementation_plan.md, walkthrough.md, revisions, scratch —
  `Sidecar`), `annotations/<id>.pbtxt`.
- **Capture:** `.db` + `-wal` as native bytes, `-shm` excluded, **never opened with SQLite** (§4.3).
- **Projection:** the SQLite layer yields row counts and timestamps even when the protobuf bodies do
  not decode, so `meta` is real and bodies degrade to `Body::Raw`. This is the case that made per-turn
  degradation non-negotiable (§5.4).
- **Why capture-only:** conversations bind to workspaces by **absolute `file:///` paths**
  (`workspace_uris`), and the IDE's index `agyhub_summaries_proto.pb` is an opaque protobuf that is not
  safely rewritable. **Open question: does the app rebuild its indexes from `conversations/` on
  startup?** If yes, restore is a file drop-in. Worth one live experiment — it is the only thing between
  this adapter and restore.
- **Deny:** the entire `%APPDATA%\Antigravity` profile — `state.vscdb` holds `antigravityAuthStatus`
  with a **plaintext apiKey**.
- **Confidence:** layout and schemas verified locally on Windows; macOS/Linux paths inferred from
  VS Code-fork conventions; resume behaviour partially inferred.

### 6.5 `copilot-chat` — GitHub Copilot Chat · **capture-only**

- **Owned by VS Code core, not the extension:** `User/workspaceStorage/<hash>/chatSessions/<uuid>.jsonl`
  (log-structured: kind 0 snapshot, kind 1 set-at-path, kind 2 append), plus
  `chatEditingSessions/<uuid>/` and `globalStorage/emptyWindowChatSessions/`.
- **Native id is the session UUID**; the `<hash>` directory is the *workspace*, not the session (§5.5).
- **Why capture-only:** the workspace hash is `md5(folderFsPath + folderCreationTimeMs)` — verified
  empirically, reproduced exactly on two real workspaces (Linux uses inode). **The same path on machine
  B yields a different hash, so sessions always orphan on a naive copy.** Restore would need to locate
  or compute B's hash dir, copy payloads in, **and merge the `chat.ChatSessionStore.index` key inside
  `state.vscdb`** — which is hazardous while VS Code runs, because VS Code caches `ItemTable` in memory
  and flushes on exit, clobbering external writes beyond normal SQLite locking. **Restore requires
  VS Code closed.** Two open questions in one adapter; capture still delivers the backup.
- **Deny:** all `*.vscdb`. Extension auth lives there as `secret://` rows encrypted by Electron
  safeStorage (Windows DPAPI, macOS Keychain, Linux libsecret) and is undecryptable elsewhere anyway.

### 6.6 `cline` — Cline · **restore**

- **Tasks are global, not per-workspace:** `globalStorage/saoudrizwan.claude-dev/tasks/<epoch-ms>/` with
  plain JSON — `api_conversation_history.json`, `ui_messages.json`. **No hash re-keying, no path
  involved.** Restore copies into the target's global `tasks/`.
- **Index:** `state/taskHistory.json` (newer) or globalState.
- **Identity:** `<epoch-ms>` — low-entropy but **not path-derived**, so §5.5 is satisfied.

### 6.7 `roo` — Roo Code · **restore**

- As Cline: `globalStorage/rooveterinaryinc.roo-cline/tasks/<id>/`, plain JSON, global.
- **One difference, and it is the adapter's only real risk:** Roo's index lives in the global
  `state.vscdb` as an extension key, so a complete restore needs one DB merge — which carries the same
  precondition as Copilot's, **VS Code must be closed**, because VS Code caches `ItemTable` in memory
  and flushes on exit, clobbering external writes.
- **Why it is still restore-capable while Copilot is not.** The difference is what the merge *buys*.
  For Copilot the workspace hash is the thing identity depends on, so without the re-key and the merge
  the session is simply not there. For Roo the task payload is global, portable and needs no re-keying —
  the merge only restores the **picker entry**. **Verify this before building:** if a restored task
  proves invisible until the index is merged, Roo's restore inherits the closed-VS-Code gate rather than
  merely preferring it. That changes the flow, not the ruling.

### 6.8 `claude-code-vscode` — Claude Code VS Code extension · **restore**

The easiest case: **the extension stores no conversations of its own.** Everything is CLI-owned at
`~/.claude/projects/…`. It exists as a distinct install of the `claude-code` adapter rather than as
separate storage: the same path on B works with zero VS Code surgery, and a different path is the same
munged-directory rename §6.1 already performs.

### 6.9 `pi` and `oh-my-pi` — **restore** (two adapters, one shared module)

- **Relationship:** pi is `@earendil-works/pi-coding-agent`; oh-my-pi is a hard fork (binary `omp`,
  versioned independently at 17.x). Separate state roots, no runtime sharing, shared session-format
  lineage. **Two adapter ids over one `pi_format` module** (§5.8).
- **Session:** JSONL tree files (`id`/`parentId`, header `version: 3`) at `~/.pi/agent/sessions/` and
  `~/.omp/agent/sessions/`, organised into **per-project dirs named by the encoded absolute cwd** —
  `E:\Projects\foo` → `--E--Projects-foo--`. Native id is the **UUIDv7** in the filename and header.
- **omp additions:** a padded title line, `title_change` / `credential_pin` entries, and a sibling
  `<session-id>/` artifact dir for overflow tool output (`Sidecar`).
- **Restore:** recompute the encoded dir for the destination project path — discovery is keyed on the
  current cwd's encoded dir. `--session <file>` is the user-facing fallback. `PI_CODING_AGENT_DIR`
  overrides the root in both; omp adds `--profile` and an opt-in XDG split on Linux/macOS.
- **Travels:** session JSONL, omp artifact dirs, pi `settings.json` (drives extension reinstall), omp
  `config.yml` and `history.db`.
- **Deny:** pi `auth.json` (plaintext OAuth/refresh + API keys, possibly `models.json`) and omp
  `agent.db` — which **fuses plaintext tokens with settings and usage in one SQLite file**, so it is
  deny-by-default in whole. Also skip `npm/`, `bin/`, `natives/`, caches, logs, and `install-id`
  (per-machine identity).
- **Compatibility:** pi → omp reads fine; omp → pi is a superset. Treat as one-way.

## 7. Multi-machine

Settled by [#13](https://github.com/seanrobertwright/session-backpack/issues/13). ADRs 0008, 0009.

Two machines sharing one vault is already **write-safe by construction** — the vault is append-only and
every manifest is sharded by machine, so concurrent captures physically cannot overwrite each other.
What remains is **meaning**.

### 7.1 A machine is one install of Backpack

Identified by a **128-bit random opaque id**, minted at first run and stored in **machine-local config —
never in the vault**. `<machine>` is a plaintext path component, so a random id leaks nothing beyond a
machine count. The human label lives only inside the encrypted manifest and machine record, so
**renaming a machine is free** — it touches no path, which matters because an append-only vault cannot
rewrite one.

**A hardware-derived id was rejected**, and it fails in both directions: it *changes* on OS reinstall,
so a machine becomes a stranger to its own backups, and it *duplicates* on cloned VMs and imaged
corporate laptops — two live installs silently sharing one shard, the single failure this scheme must
not have. It is also a stable cross-application fingerprint parked in a cloud provider's folder.
**The human label as the id was rejected** because it leaks the user's name to the sync provider and,
being mutable, would strand history on rename.

**Accepted consequence:** reinstalling Backpack mints a new machine. The old shard stays in the vault and
nothing writes to it again. This is honest rather than harmful, and it is where the label earns its
keep — the UI presents the shard as *`sean-desktop` (retired)*. Defining a machine as *an install* also
means the answer to *which machine am I?* comes from a file the app itself wrote, rather than from
hardware that lies.

**Known limitation, stated not solved:** a cloned VM that copies the local config carries the same
machine id, so two live installs share a shard. Detecting this reliably needs a liveness heartbeat — a
write on every run — which is real cost for a rare event, and §8 removed the only mechanism that would
have wanted one.

**Machine records** are append-only at `machines/<machine-id>/<ts>.mf.age`:

```jsonc
{ "label": "sean-desktop", "os": "windows",
  "status": "active" | "retired", "first_seen": "…" }
```

Written on **first run, label change and explicit retirement only** — never per capture — so a vault
accumulates a handful over its lifetime. Structurally identical to session manifests, so they are
conflict-free for the same reason and need no new folding logic.

Manifests *also* carry `machine: { id, label, os }` redundantly. That redundancy is deliberate: it lets
a human decrypt one manifest with the bare `age` CLI and see which machine wrote it, without the
registry. Deriving the label from the newest manifest instead was rejected — an append-only vault
freezes a stamped label at capture time, so a machine renamed then retired is mislabelled forever, and
a machine that has never captured anything would not exist in the vault at all.

Machine records are **not** in `vault.json`, for the same reason nothing else is: that is the only
mutable file in the vault and therefore the only routine conflict candidate. It should change on a
format bump or a recipient change, not on every rename and install.

### 7.2 Restore preserves session identity where the tool's identifier permits

> **Preserve the native id; re-key only where the identifier is path-derived and cannot survive
> re-homing.**

Whether it survives is a property the adapter already knows, so it is asked rather than guessed.
Identity belongs to the **tool**, not to Backpack — a backup tool that renames what it restores is not
restoring. The technical edge is sharper still: Claude Code's transcript carries `sessionId` on *every*
JSONL line, so minting a new id means rewriting file **contents**, which ADR 0006 forbids.

The exception is not a hedge but a physical fact: **Gemini keys sessions on a hash of the absolute
project path**, so re-homing *necessarily* re-keys. Preservation is unavailable, not declined.

Every restore stamps provenance onto the resulting manifest:

```jsonc
"restored_from": { "opaque_id": "…", "machine": "…", "captured_at": "…" }
```

*Always minting a new id* was rejected: uniform and collision-free, but it costs the thing the tool
exists for. Your session returns as a stranger, and the vault fills with unexplained near-duplicates,
permanently.

**Accepted consequence:** with ids preserved, two machines can both continue the same session and
diverge. The layout absorbs this without drama — separate shards — so both histories survive and neither
can overwrite the other. **The vault records a fork, truthfully.**

### 7.3 Branches fold when they agree, fork when they don't

The session browser shows **one entry per session**. Behind it, the reader classifies the branches:

| Evidence | Meaning | Behaviour |
|---|---|---|
| Newest transcript **blob hashes match** | Same bytes — two copies of one thing | **Fold** silently |
| B's chain carries `restored_from` into A, and A has nothing newer | B continued the session | **Fold**; B's tip is the session's tip |
| Both branches have captures after the shared ancestor | Genuine divergence | **Declare a fork** |

Two properties make this work rather than merely sound reasonable. The classification is
**evidence-based, not heuristic** — content addressing gives *identical* for free because the blob name
*is* the plaintext hash, and `restored_from` gives real ancestry instead of inferring it from turn
counts and timestamps, which would be a guess dressed as a fact. And it reads **manifests only**, so the
hydration rule (§3.5) holds.

*Merging all captures into one timeline* was rejected: when branches have diverged, "newest by wall
clock" is a lie that destroys work — a laptop waking at 4pm and backing up its stale copy would outrank
the desktop's real 200-turn session from 11am. **Silent loss is the one outcome this design refuses.**
*One list entry per machine* was rejected for inflicting the rare case on the common one: overwhelmingly,
exactly one machine ever captures a given session.

**Accepted limit: divergence is declared, never merged.** Two forked branches stay two forever.
Stitching a conversation back together is a different product (§12). §10.5 specifies how a fork is
drawn.

### 7.4 Collision

```rust
pub enum Collision {
    Skip,       // leave the existing session untouched; report it
    Replace,    // supersede it — see the safety rule
    KeepBoth,   // re-key the restored copy to a fresh native id
}
```

Resolved **per session, as a unit** — never per file — because a session is restored as a unit. There is
deliberately **no `Prompt` variant**: the value must arrive already decided, so prompting is the UI's job
and it resolves to one of these three before the call. `KeepBoth` knowingly breaks §7.2's
identity-preservation rule, but as an *explicit user choice* rather than a silent one, and it reuses the
re-keying mechanism the Gemini adapter already requires.

**`Replace` first captures the existing session into the vault, and is unreachable from any code path
that has not.** This is nearly free — append-only and content-addressed, so it costs one manifest plus
whatever blobs are not already stored — and it converts the most dangerous variant into a recoverable
one. **`Replace` means supersede, not destroy.**

**Default: `Skip`.** It makes restore **idempotent**, which is what people actually need when a large
restore is interrupted and resumed. And a collision means something unexpected is true — live work
exists under an id you believed was only in the vault — which deserves attention rather than an
automatic answer. Skip reports it; the UI then offers Replace or KeepBoth per session, showing §7.3's
branch comparison so the choice is informed.

**Toolstate inverts the case.** Collision is the *normal* state — every configured machine already has a
`settings.json` — so `Skip`-as-default would make toolstate restore a no-op on exactly the machines you
would use it on. Toolstate therefore restores **per `FileRole`** (`Settings`, `Mcp`, `Memory`), **opt-in
with nothing preselected**, replacing a chosen role wholesale after capturing the machine's existing
files for that role. *"Bring my MCP servers, not my keybindings"* is answered by selecting `Mcp`.

**Merge was rejected**, genuinely tempting though it is for `Mcp` where unioning server entries is the
obvious wish. It means per-tool, per-format merge logic (JSON, TOML, and whatever comes next), each with
its own conflict semantics — a large permanent surface for one convenience.

**Hazard stated, not solved:** toolstate is restored **verbatim** and frequently contains machine-specific
absolute paths — an MCP entry pointing at `C:\Users\sean\…` does not work on a Mac. **Backpack warns and
does not rewrite** (§10.6). Rewriting config *contents* is the same line ADR 0006 refuses to cross.

### 7.5 Concurrency

Both maintenance jobs — conflicted-copy reconciliation (§3.6) and compaction (§8) — run from **any
machine, with no lock and no designated collector.** The reasoning is §3.6's: assignment can only add a
way for the work to stop happening.

## 8. Compaction

Settled by [#19](https://github.com/seanrobertwright/session-backpack/issues/19). ADR 0010.

> **v1 compacts, it does not collect. Nothing is ever forgotten.**

### 8.1 Compaction is not retention

Two operations were hiding under one name, and separating them is the whole section:

- **Compaction** — dropping blobs that carry *no unique information*. No policy, no promise, **no way to
  lose data**.
- **Retention** — deliberately forgetting history the user might still want. A promise, a settings
  surface, and a real way to lose data.

*Deletion never happens on a guess* bites completely differently on the two. Retention's guess is
**whether the user still wants a thing**, which is unknowable. Compaction's is **whether a blob's bytes
survive elsewhere**, which is a fact. **v1 only answers the decidable one.** There is no keep-N, no time
window, no size budget, and no *your vault is N GB, reclaim M GB* prompt. Retention is out of scope
(§12).

The prize, priced against §4.5: compacting to one blob per session takes ~6.3 GiB/yr/tool/machine down
to ~1.9 GiB, so **~4.4 GiB/yr is reclaimable** — concentrated entirely in the chatty p90 tail, with
most sessions never touched by the compactor at all.

### 8.2 The basis: a forward-recorded prefix proof

Blobs are whole-file, and every capture is a byte-exact prefix at a record boundary (§4.2). For a file
that only grows, capture N's blob content is therefore entirely *contained in* capture N+1's. That is
the redundancy worth reclaiming. The question was how to **know** it, given the hydration rule forbids
reading blobs.

**The core records the proof at capture time**, while the new bytes are already in hand: it hashes the
**first L bytes** — where L is the previous capture's blob length, taken from the previous *manifest* —
and checks it against the previous blob's hash. **No old blob is read; nothing hydrates.** The successor
manifest then carries, per file:

```jsonc
"supersedes": { "blob": "<hash of the predecessor>", "len": 2280104 }
```

**Forward-recorded on the successor, never stamped on the predecessor** — manifests are write-once, so
the field must point backwards from a new file rather than mutate an old one.

Three properties this buys:

- **It is an observation, not a claim.** Deletion happens on bytes that were checked, at the one moment
  they were legitimately in memory.
- **Failure is safe by default.** No proof means no deletion. A rewritten file, a `/compact`, a tool
  that rotates its log, a torn-then-rewritten tail — all simply **stop being compactable**. None become
  data loss.
- **It is per-file, not per-capture.** A session whose transcript appends while a sidecar is rewritten
  compacts the transcript and keeps every version of the sidecar.

*Letting the adapter declare a role append-only* was rejected: it puts a destructive operation
downstream of an **untrusted declaration** — exactly the boundary ADR 0005 exists to hold — and it is
unverifiable by construction. One wrong line in a descriptor would become silent data loss.

The first capture of a session has no predecessor and so no `supersedes`. The field is additive; no
`format_version` break.

### 8.3 Manifests are never deleted

**Only blobs are.** The vault stays append-only for the file type that gives it its safety.

This is not separable from the rest, though it looks it. Blob X is not unreferenced — it is referenced
by its own manifest — so deleting it appears to leave a dangling reference that verify-on-read would
report as corruption forever. *Deleting the superseded manifest alongside its blob* was rejected: it
loses the record of *when* captures happened, and makes compaction the first operation that deletes a
manifest, a far bigger crossing than deleting a blob. *Folding a shard's superseded manifests into one
replacement* was rejected too: it introduces the first manifest that is not a record of a capture, and
still deletes manifests to save bytes that are already negligible.

The cost of keeping them is one new legitimate state for verify-on-read: **absent by design** (§3.5).

### 8.4 The invariant

> **A blob may be deleted iff a surviving proof chain reconstructs it from a blob that still exists.**

That single line replaces mark-and-sweep outright. **The collector never asks who references a blob.**
It asks only whether the blob is reconstructible. Because manifests are never deleted, a proof chain can
never break; and because prefix containment is transitive, X ⊂ Y ⊂ Z keeps serving X after Y is itself
compacted. **There is no referenced set to compute, and therefore no way to compute it wrong.**

**This is what defuses the sync hazard.** The danger — machine B's blob synced ahead of its manifest
looks unreferenced to machine A, which deletes live data — **cannot occur**, because A never deletes on
*absence of evidence*. It deletes only on the *presence of a proof*, and the proof is itself the recovery
path. A manifest arriving an hour later and referencing a compacted blob is served through the chain like
any other read.

**The counterintuitive corollary, stated explicitly because it will look wrong in review:** blobs are
content-addressed and shared across sessions and machines, so blob X may be the *tip* of some other
machine's shard while being a compactable prefix in this one. **It is still safe to delete**, because
reconstructibility is a property of the blob, not of who points at it. That other machine's read resolves
through this machine's proof.

**Verify before delete.** The recorded proof was written against real bytes and is probably right, but a
bug writing a wrong `supersedes` is the one unrecoverable failure left, so the collector re-verifies:
hydrate the survivor **once**, stream it, and hash at every prefix length in the chain — verifying
X₁ ⊂ X₂ ⊂ … ⊂ Xₙ ⊂ Y in a **single pass, one blob read per chain**. This is a targeted carve-out from the
hydration rule (§3.5), not a sweep. Verification failure is not a crash: the chain is left alone and
nothing is deleted.

**Grace period: 7 days.** The remaining hazard is the mirror image of the sync race: machine A deletes X,
then dies or fails to upload before survivor Y propagates. So **both the survivor blob and the proof
manifest must be older than 7 days** before X may be deleted. The real bound is sync propagation lag —
hours at worst — so an enormous margin costs essentially nothing here, and it incidentally covers a laptop
that only syncs weekly.

### 8.5 When it runs

**A weekly idle sweep. That is the only trigger**, scheduled alongside the watcher in the tray/idle
loop.

*Piggybacking on capture* was rejected: it is near-empty in practice, because the 7-day grace means
nothing in a freshly-written chain is eligible — and it is *structurally* incomplete, since a session
captured five times in a day and then abandoned would never be revisited, and that is precisely the chain
holding the biggest prize. A revisiting sweep is required regardless, and once it exists the capture-time
pass earns nothing.

The sweep is cheap because **proofs come from the local SQLite index**, not from the vault. It reads
nothing from the synced folder until it has a specific chain to verify, and the candidate set comes from a
**directory listing** of `blobs/`.

**Scope: the machine's own shard only.** This is a **politeness rule, not a safety one** — compaction is
safe from anywhere. It exists because verification hydrates the survivor: on the machine that *wrote* the
chain those bytes are already local and verification is free, while on any other machine it is a full
download of a possibly-100 MB blob to reclaim space the owner can reclaim for nothing. Own-shard routes
the work to the machine that already has the bytes **without designating anything**, so it does not
reintroduce the lost-machine failure §3.6 rejected.

**Accepted residue:** a retired machine's chains, and your own chains from before a reinstall (§7.1 mints
a fresh machine id, orphaning the old shard), are **never compacted**. They are kept forever. That is the
safe direction, and it is bytes rather than correctness.

### 8.6 Fully invisible

**No prompt, no setting, no progress UI, no "Compact now" action anywhere — not even in an advanced
pane.**

Compaction is lossless, so there is genuinely nothing for the user to decide. Any control would teach them
that a decision exists and invite them to worry about a mechanism whose whole point is that it cannot cost
them anything. The most that surfaces is the read-only vault size already shown in settings, which will
simply be smaller.

### 8.7 The v1 reader requirement

> **v1's reader must understand proof-chain reconstruction from day one, even though the compactor will
> rarely have run by then.**

This is the one mixed-version trap in the design, and **it is only avoidable now.** A build that does not
understand `supersedes` reads a compacted capture, finds a missing blob, and reports a healthy session as
corrupt. Bumping `min_reader_version` **cannot fix it**, because the manifest an old build chokes on is
the *superseded* one — unchanged and perfectly parseable — while the proof lives on the *successor*.

The blast radius is limited (quarantine is local, so one machine's false alarm never propagates as fact),
but the user still sees a corruption warning on intact data. Since v1 is the first release there are no
older builds, so shipping reconstruction in the v1 reader closes the hole permanently and costs nothing.

**The reader's missing-blob resolution path:** walk the proof chain → decrypt the survivor → truncate to
`len` → verify the result against the absent blob's own hash (free, since blobs are named by plaintext
hash) → serve. Report **absent by design**, never *missing*.

## 9. Security

Settled by [#14](https://github.com/seanrobertwright/session-backpack/issues/14). ADR 0007.

### 9.1 Key architecture

**A per-vault X25519 keypair**, not direct passphrase encryption of every file.

- The vault's **public key lives in plaintext** in `vault.json`. This is the load-bearing choice: it
  means **every machine can encrypt new backups unattended, forever.** Auto-watch never needs an unlock
  and survives reboots with zero prompts.
- The **private identity** is stored in the vault at `identity.age`, passphrase-wrapped with age's
  scrypt passphrase encryption (library defaults; no custom KDF tuning).
- The vault stays recoverable with the standalone `age` / `rage` CLI (`age -d -i identity.key`) — **no
  Backpack required.** This is a design goal, not a side effect, and it is why §3.2's layout keeps tool
  names readable and manifests per-session.

This supersedes the stack research's provisional *scrypt passphrase recipient* call, which was made
before the unattended-backup question was examined. Everything stays within age 0.12's capabilities.

### 9.2 Unlock UX — one passphrase per machine, ever

- The prompt appears **lazily, on first protected action** (open a session, restore, export) — **never
  at app launch, and never for a backup.**
- The dialog carries **"Remember on this device", default checked**, which stores the **decrypted
  identity** — never the passphrase — in the OS keychain (Windows Credential Manager / macOS Keychain /
  libsecret) via `keyring` 4.1.
- Net effect: **one passphrase entry per machine, ever.** A user who runs Backpack purely as a silent
  backup daemon never types the passphrase after vault creation at all.
- Unlock state is **ambient in the UI, never a modal** — a quiet *Unlocked · remembered on this machine*
  line (§10.2).

### 9.3 Recovery

A **second X25519 identity is generated at vault creation**, and **every file is encrypted to both
recipients from byte one** (age multi-recipient, roughly one header line of overhead). Adding a
recipient later could not retro-protect existing files, which is why it happens at creation or not at
all.

- The recovery key is **shown once**, printable and saveable, and **never stored by Backpack**.
- Any machine with a cached identity can reset the passphrase (a re-wrap) without the recovery key.
- **Lost passphrase + lost recovery key + no cached machine = lost vault.** Stated plainly at creation,
  not buried.

**Passphrase change is a re-wrap only**: instant, no vault re-encryption. The UI says so honestly —
changing the passphrase does not protect existing backups from someone who already holds the old wrapped
identity and the old passphrase. **Full key rotation is out of scope** (§12); the manual escape hatch is
to create a new vault and restore into it.

### 9.4 Sanitized export

For sharing a session as plaintext.

- **Scope exclusion is non-negotiable: transcripts only.** Settings, MCP configs and memory never
  export. (Known secret *files* never entered the vault in the first place, §5.2.)
- **Pattern redaction**, honestly labelled best-effort in the UI: known token shapes (`sk-…`, `ghp_…`,
  `AKIA…`, JWTs, PEM blocks), high-entropy strings in env-var-looking contexts, and home-path /
  username masking, replaced with readable `[REDACTED:api-key]` markers.
- **A default-on review pane** as the final step: every redaction listed with surrounding context before
  a single plaintext byte is written.
- **The review pane is the reader in `redact` mode — the same component**, so what you review is what
  you read. Two renderers over one type would be free to drift, and you would end up reviewing something
  that does not look like what you read.

**Export fails closed.** Only `Text`, `ToolCall` and `Thinking` travel. `Attachment`, `Opaque` and `Raw`
are **omitted behind a visible, counted stub**:

```
┌─────────────────────────────┐
│ 1 image omitted             │
│ 3 undecodable turns omitted │
│ 88 system events omitted    │
└─────────────────────────────┘
```

All three are un-redactable in principle. **No regex cleans a screenshot of a `.env` file.**
Pattern-matching bytes whose structure you failed to parse is theatre. And `Opaque` is hidden by default,
so a reviewer would never lay eyes on it — the sampled transcript has hook `stdout` embedded in exactly
those records. Since the review pane exists precisely because redaction is untrustworthy, shipping
content the redactor provably cannot clean would undo it. Failing closed is cheap here: the native file
can always be exported deliberately.

### 9.5 Threat model

| Adversary | Sees | Does not see |
|---|---|---|
| **Sync provider / anyone who can list the folder** | Which tools you use, roughly how many sessions, how many machines, when you worked, vault size | Project paths, client names, folder layouts, native session ids, machine names, any content |
| **Attacker with folder access, no passphrase** | The above | Everything else — every blob and manifest is age-encrypted |
| **Attacker with folder access who can guess a `native_id`** | Whether that specific session is in the vault | Its contents. And §5.5's rule makes every native id a high-entropy session identifier, so this is not a path-guessing attack |
| **Attacker with the old passphrase + old wrapped identity, after a passphrase change** | Everything | — (stated in the UI; §12 records full rotation as out of scope) |

**No credential ever enters the vault** (§5.2), so a compromised vault never yields a live token for any
agent tool.

## 10. Interface

Settled by [#16](https://github.com/seanrobertwright/session-backpack/issues/16); §10.4–§10.7 are the
spec inputs the map routed here rather than ticketing, each with **no decision left in it, only
writing**.

### 10.1 One global view shape

Console, Navigator and Timeline are not three apps but **three shapes over the same two nouns** —
captures and sessions. Same data, same actions, same reader; only the navigation differs. **All three
ship and the user picks one.** The preference is **global and singular**, governing Home and Sessions
together, rather than being set separately per surface — which would have meant nine hybrids instead of
three intact directions.

| Shape | Home | Sessions |
|---|---|---|
| **Console** | Shield band + stat strip + "Needs attention" | Dense table, inline session detail |
| **Navigator** | Vault pane — path, encryption, stat tiles, exceptions, machines | List + reading pane |
| **Timeline** | Health ribbon + machine lanes + recent capture stream | Capture spine + scrubber, session opens over the top |

**The shell sits outside the shape.** The rail (Home / Sessions / Machines / Settings), the filter
facets, the current filter and the selected session are owned by the shell. Filter to `pilot` in
Timeline, switch to Console — still `pilot`. **Without that, the switcher would be three apps in a
trenchcoat.**

The preference is machine-local (§2.3). A first-run user never has to choose: there is a default and the
switcher is a control they can ignore forever.

### 10.2 Design rules that hold across all shapes

1. **Every Home shape answers *am I safe?* above the fold.**
2. **Restore is a per-session action beside Export**, in the session header — not a wizard.
3. **Unlock state is ambient, never a modal** — a quiet *Unlocked · remembered on this machine* line
   (§9.2).
4. **Machines are a first-class, colour-coded dimension**, not a filter buried in settings.
5. **Adapter health is a list of exceptions**, not a wall of green ticks. Healthy adapters stay quiet,
   and **idle ≠ needing attention.**

### 10.3 Theming

- **Auto is the default**: follow the OS — Slate in dark, Paper in light, nothing to configure. It is an
  explicit fourth option in the picker, not a hidden state.
- **Terminal ships as a real user-facing option.** It swaps typeface and corner radius as well as
  palette, which is what proves the token seam holds for skins that change more than hue.
- **Mechanism:** all colour is CSS custom properties on `:root`; a skin is a re-declaration behind
  `[data-skin]`. **Semantic colour is a separate axis from the accent**, so status never competes with
  branding. The chrome is cold; warmth means something.

### 10.4 Reading, and how degradation surfaces

> **Loud where you read, quiet in the list, absent from the dashboard.**

| Surface | Behaviour |
|---|---|
| **Reader, per turn** | `Body::Raw` renders as a visibly marked block. **Never hidden.** `Body::Opaque` is hidden by default with a reveal control. `Thinking` is collapsed by default. |
| **Reader, whole file** (`project()` → `Err`) | A banner — *"Could not parse this session. Bytes are intact; restore is unaffected."* — above the native bytes decoded as **lossy UTF-8** (invalid sequences → `U+FFFD`), monospaced and scrollable, with **Export native file**. |
| **Reader, version skew** | A session captured by a newer Backpack than this build shows *captured by a newer Backpack* — a fourth state, distinct from a parse failure, because the bytes are fine and the **reader** is behind. |
| **Session list** | A quiet `partial` badge, from `meta`'s `raw_turns` / `opaque_turns`. Advisory and **pessimistic-only** — it can over-warn, never under-warn — and it self-corrects on open, when the local adapter re-projects. |
| **Dashboard** | **Never counted as an exception.** |

**The dashboard rule is deliberate.** The app is positioned around *am I safe?*; surfacing *3 sessions
unreadable* there teaches users that a healthy vault is broken — and Antigravity would light it up
permanently **by design** under its capture-only ruling. A parse failure is **not data loss**: native
bytes are stored, restore stays byte-exact, and a later `adapter_version` silently repairs the reading of
all history.

Lossy UTF-8 beats the alternatives because of what failures actually look like: the likely case is a
JSONL variant the parser did not expect, where the conversation is plainly readable even though the
structure defeated us. A hex/strings pane is a developer tool in a consumer app; export-only would
discard readable text already held in memory.

**Subagent threads** are listed separately from the main conversation, labelled from the companion's
`description` (§5.4) — never from truncated prompt text, which reads as a wall of instructions, and
never as `Thread 1 … Thread 8`, which makes eight identical rows you must open one at a time.

### 10.5 Forked-session presentation

A fork (§7.3) is drawn as **one session entry that expands into its branches** — not as two sibling
entries, which would inflict the rare case on the common one, and not as a bare badge, which announces a
problem without offering the comparison needed to act on it.

- The list shows **one row per session** with a **fork marker** and the branch count.
- Expanding shows one line per branch: **machine (colour-coded, §10.2 rule 4), turn count, time range,
  last captured** — every field already present in `meta`, so **expanding decrypts no transcript.**
- Opening a branch opens the reader on that branch. The shell's selected-session state (§10.1) tracks
  the branch, so switching view shape holds the branch too.
- **Restore asks which branch**, presenting the same comparison. It never picks.
- There is no merge action anywhere in the UI, because there is no merge (§7.3).

### 10.6 First-run and onboarding

Every constituent is already decided; sequencing them is writing, not deciding.

**Install.** The user has just crossed one scare-wall (§11.2) — SmartScreen *More info → Run anyway*, or
macOS *Open Anyway* under Privacy & Security. The download page walks through it explicitly rather than
leaving them at the dialog, and states that **the toll is paid once at first install and never on
updates**, along with the `SHA256SUMS` and `gh attestation verify` provenance story (§11.3).

**Creating a vault.** Pick a folder → set a passphrase → save the recovery kit.

- The folder picker's guidance is *choose a folder your sync tool already watches*, with the vault's
  growth budget stated honestly (§4.5) alongside the fact that OneDrive free is 5 GB.
- The recovery kit is **shown once**, printable, with *lost passphrase + lost recovery key + no cached
  machine = lost vault* stated plainly (§9.3). This screen cannot be skipped, only acknowledged.
- The machine mints its random id here and writes its first `machines/<id>` record (§7.1). The user is
  asked for a **label**, defaulted from the hostname.

**Pointing a fresh machine at an existing vault.** The second-machine flow, and the one that must be
smooth because it is the product's whole premise.

1. Pick the existing vault folder. Backpack reads plaintext `vault.json`, recognises it, and shows what
   it can see **without unlocking**: vault id, created date, machine count, session count.
2. **This machine mints a new machine id** — it does not adopt or claim any existing one (§7.1).
3. **No passphrase is requested yet.** Backup starts immediately, because the public key is plaintext
   (§9.1). The user can walk away with backups already running.
4. The passphrase is requested **lazily, the first time they open a session** — with *Remember on this
   device* checked (§9.2). **One prompt, once, ever.**
5. UI preferences start at defaults; there is no "adopt my desktop's setup" (§2.3).

**Detection.** On first run Backpack runs every adapter's `detect()` and shows what it found. Tools that
are not installed are absent, not listed as errors (§10.2 rule 5). Capture-only adapters are labelled as
such at this point, honestly, rather than at the moment a user first tries to restore.

### 10.7 Surfacing permanent capture failure

The stability check discards and re-arms silently (§4.2), which is right for a transient lock and
**wrong forever**. A session whose files are permanently locked would never be captured and **the user
would never be told** — silent permanent non-capture contradicts the entire purpose of the product.

- The core tracks **consecutive discarded attempts per session** in the local index.
- After a session has been discarded repeatedly across a **span measured in days rather than a count of
  attempts** — the failure that matters is *this has not been backed up for days*, not *this retried
  twenty times* — it becomes an **exception**.
- Exceptions appear in the **"Needs attention"** list on every Home shape, naming the session, the tool
  and how long it has gone uncaptured, with the file that will not stabilise.
- **This is the one degradation that does reach the dashboard**, and the distinction is exactly §10.4's:
  a parse failure means *stored but hard to read*, while this means **not stored at all**. The dashboard
  answers *am I safe?*, and here the honest answer is no.
- It clears itself the moment a capture succeeds.

## 11. Distribution

Settled by [#15](https://github.com/seanrobertwright/session-backpack/issues/15).

### 11.1 Artifacts

| OS | Human download | Updater artifact | Notes |
|---|---|---|---|
| Windows | NSIS `-setup.exe` | same | **Per-user install** to `%LOCALAPPDATA%` — no UAC, so the user faces one warning (SmartScreen) rather than two |
| macOS | `.dmg` | `.app.tar.gz` | The updater cannot consume a `.dmg`, so both ship. `.app` is ad-hoc signed. |
| Linux | `.AppImage` | same | No signing gate |

**Architectures:** macOS **universal** (Intel + Apple Silicon `lipo`'d into one binary, one `.dmg` — no
architecture choice at the download page, which removes the most common macOS install failure); Windows
**x64** (Windows-on-ARM runs it emulated); Linux **x86_64**.

**Deliberately excluded:** MSI (machine-wide → UAC on an unsigned binary; Backpack's user is an
individual developer, not an IT department); `.deb` / `.rpm` (the updater cannot replace a
distro-package install, so those users would silently fall off the update channel); Flatpak (sandboxing
directly obstructs the arbitrary filesystem access Backpack needs — `~/.claude`, `~/.codex`, `~/.gemini`,
plus a user-chosen sync folder anywhere on disk). **Every artifact v1 ships is auto-updatable.**

**Channel: GitHub Releases only.** No winget, Homebrew cask or AUR (§12). winget's validation pipeline
runs Defender and SmartScreen checks that unsigned installers routinely trip; a Homebrew cask still
deposits the user in front of Gatekeeper, so it removes no warning; and each channel is a second update
path that can drift from the in-app updater. **One download page, one update path.**

### 11.2 Code signing — none purchased in v1 ($0)

Accepted cost: the SmartScreen *Windows protected your PC* wall (bypassable via *More info → Run
anyway*) and the macOS Gatekeeper block (*System Settings → Privacy & Security → Open Anyway*).

Two things make this cheaper than it looks:

- **Both warnings are triggered by a browser-applied provenance tag** — `com.apple.quarantine` on macOS,
  the Mark-of-the-Web alternate data stream on Windows. Artifacts fetched by `tauri-plugin-updater` from
  *within the app* are not tagged, so **the toll is paid once at first install, not on every update.**
  This is why keeping users on the in-app updater matters more here than it would for a signed app.
- **Linux has no signing gate at all**, so one of three platforms is unaffected.

**Not optional despite "unsigned": the macOS `.app` must be ad-hoc signed (`codesign -s -`) in CI.**
arm64 macOS refuses to execute a binary carrying no signature whatsoever — it dies with SIGKILL rather
than showing a dialog. Ad-hoc signing is free and needs no Apple account, but **without it v1 does not
run on any M-series Mac.**

**Recorded for future-us:** SmartScreen reputation is a **clock, not a switch**. It only starts when a
certificate is first used, and it **resets if the signing identity later changes.** "Unsigned in v1"
therefore means *deferred*, not *settled*; ~$219/yr (Apple $99 + Azure Trusted Signing ~$120) is a known
future line item, not a rejected one.

### 11.3 Provenance

Every release publishes **`SHA256SUMS`** covering all artifacts, and **GitHub build attestations** via
`actions/attest-build-provenance` — Sigstore-backed, free, one CI step, verifiable by anyone with
`gh attestation verify`. Documented in the README as the trust story that replaces a certificate.

Worth stating plainly: this is a **stronger** claim than an OV certificate makes. **A certificate proves
who paid for it; an attestation proves which commit and which workflow produced this exact binary.**

### 11.4 Updates

`tauri-plugin-updater` against a **static `latest.json` on GitHub Releases** — no vendor, no hosted
service.

- Checks **on launch and roughly every 24 h**. **Stable channel only** in v1.
- **Prompts before download and before install — never silent.** A backup utility that replaces itself
  unannounced is a poor look for a trust-sensitive tool, and the user must be able to sit out a bad
  release.
- **Refuses to install while a backup is in flight** — finish or defer. Backpack is a tray app that may
  be mid-capture and holds a decrypted age identity cached from the OS keychain.
- **The minisign private key lives as a CI secret with an offline backup.** Losing it orphans every
  existing install, which will reject all future updates. **This key is as important as the vault
  passphrase** and is called out in the release runbook.

Prompt-before-install *guarantees* version skew across a user's machines — which is why §3.4 exists.

## 12. Out of scope for v1

Each was consciously ruled out, with the ticket that ruled it. **None is a rejection of the idea**
unless stated.

| Ruled out | Why |
|---|---|
| **Any ability to forget** — retention policies, keep-N, time windows, size budgets, reclaim prompts | Deliberately forgetting is a policy, a promise and a real way to lose data. *Deletion never happens on a guess* makes it the one vault question not decidable from evidence: whether a user still wants a thing is unknowable, whereas whether a blob's bytes survive elsewhere is a fact. **Pressure that would reopen it:** ~6.3 GiB/yr/tool/machine crosses OneDrive's 5 GB free tier inside a year ([#19](https://github.com/seanrobertwright/session-backpack/issues/19)) |
| **Promoting capture-only adapters to restore-capable** | The *rule* is fixed (§1.3) and acting on it is one `Restorer` impl (§5.9). What remains is a post-v1 release process, waiting on evidence that does not exist yet: Antigravity's index-rebuild question ([#5](https://github.com/seanrobertwright/session-backpack/issues/5)), Copilot's `state.vscdb` merge safety ([#6](https://github.com/seanrobertwright/session-backpack/issues/6)) |
| **Cross-tool full-text search** | Deliberate fast-follow. The index already bundles FTS5 ([#9](https://github.com/seanrobertwright/session-backpack/issues/9)) |
| **Built-in cloud sync backend or accounts** | The vault rides the user's own synced folder. This is the product ([#8](https://github.com/seanrobertwright/session-backpack/issues/8)) |
| **Running or resuming sessions inside Backpack** | It is a vault and a browser, not an agent client |
| **General dotfile management beyond agent state** | — |
| **Merging forked session branches** | Forks are shown and chosen between, never stitched. Reconciling divergent conversations is a different product ([#13](https://github.com/seanrobertwright/session-backpack/issues/13)) |
| **Making restored configs portable** | Rewriting machine-specific absolute paths inside restored `Settings`/`Mcp`/`Memory`. Toolstate restores verbatim and Backpack warns instead (§7.4); rewriting config *contents* is the line ADR 0006 refuses to cross. A real feature, but a different one ([#13](https://github.com/seanrobertwright/session-backpack/issues/13)) |
| **Syncing UI preferences across machines** | Buying the day-one convenience means parking presentation state in the shared append-only vault permanently ([#13](https://github.com/seanrobertwright/session-backpack/issues/13)) |
| **Third-party adapters without a rebuild** | No declarative TOML adapters, no dynamic plugins. The trait boundary already satisfies "without touching core" (§5.8). Declarative adapters remain the likely eventual answer, and the shipped adapters are built as thin data over a shared JSONL projector to prove that path internally first. Dynamic plugins are a firmer rejection: they fight the deny backstop, whose premise is that adapters are untrusted ([#12](https://github.com/seanrobertwright/session-backpack/issues/12)) |
| **Full vault key rotation** | v1 ships passphrase re-wrap only; the compromised-vault case is handled manually — create a new vault, restore into it ([#14](https://github.com/seanrobertwright/session-backpack/issues/14)) |
| **Package-manager distribution and purchased code-signing** | Both post-v1, not rejections. Note the trap: SmartScreen reputation is a clock that only starts when a certificate is first used, and resets if the identity changes (§11.2) |
| **Delta storage (`segments[]`)** | Retrofittable additively; §8's compactor claims most of the prize with no format change (§4.5) |
| **Splicing subagent turns inline at the spawning call** | The most faithful reading experience, and `toolUseId` proves it is achievable for Claude Code — but it needs cross-file correlation with per-tool linking rules. Nothing here forecloses it ([#18](https://github.com/seanrobertwright/session-backpack/issues/18)) |
| **Scheduled integrity scrub** | Would hydrate the whole vault (§3.5). An opt-in manual check, with the download cost stated up front, remains available later |
